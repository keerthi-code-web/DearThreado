🧵 DEARTHREADO
MASTER ANTIGRAVITY IMPLEMENTATION SPECIFICATION
Document status
STATUS: LOCKED
This document is the implementation contract for the DearThreado project.
Antigravity must implement this specification. It must not independently redesign the product, invent features, remove requirements, change workflows, or substitute its own interpretation for the decisions stated here.

1. PROJECT IDENTITY
Product name
DearThreado
The name represents the idea of a meaningful connection between people through handmade and personalized gifts.
The thread is a central brand metaphor:
connection between thought → creation → person → memory.
The project is not intended to feel like a generic e-commerce marketplace.
It should feel like:
A beautiful little place where someone can find something meaningful for someone they care about.

2. BRAND IDENTITY
Primary tagline

Supporting emotional message

Additional brand thought
Only special persons deserve handmade gifts.
This phrase may be used selectively in an appropriate emotional/brand area.
It must not be repeated unnecessarily.

14. CUSTOMER ACCESS
Visitors may browse without registering.
Authentication becomes mandatory when a customer needs an authenticated action.
Authentication-required actions
Ordering
When an unauthenticated customer attempts to proceed with an order:
Show a DearThreado-themed message/modal explaining that an account is required.
Example tone:
Your first DearThreado order needs a little introduction. Please register or log in to continue.
Then redirect to:
Login / Register
After successful authentication:
Return the customer to the point they were at before authentication.
Do not dump the customer back to Home unnecessarily.

21. CUSTOMIZATION SYSTEM
This is a core feature, not an optional decorative addition.
Customization belongs to the product definition.
Customer customization belongs to the specific cart/order item.
For example:
Product
 └── Customization Fields
       ├── Photo
       ├── Text
       └── Instructions
Different products may have different fields.
Possible field types include:
image upload 
text 
color 
size 
quantity 
descriptive/instruction input 
Only applicable fields should appear.
Required fields must be validated.
The backend must not blindly trust frontend customization data.
The blueprint explicitly requires customization definitions to belong to products and customization values to remain associated with individual cart/order items. 

22. MULTI-PRODUCT CART
One customer may have multiple products in the cart.
Each cart item must preserve its own customization.
Example:
Cart

Product A
 └── customization A

Product B
 └── customization B
Two instances of the same product with different customization must remain distinguishable.
This is explicitly part of the project's intended architecture. 

23. CHECKOUT
Checkout collects the required delivery information.
Customer must be authenticated before order creation.
Required flow:

 ↓

 ↓

 ↓

 ↓

 ↓

 ↓

24. PAYMENT
MVP payment method:
Cash on Delivery
Initial payment status:
Pending
After delivery/payment verification:
Paid
The backend must calculate/verify the actual order total.
Never blindly trust a total supplied by the frontend.

25. ORDER WORKFLOW
Strict state flow:
Placed / New
      ↓
Confirmed
      ↓
Preparing
      ↓
Shipped
      ↓
Delivered
Cancellation is permitted only before Preparing begins.
Once an order enters:
Preparing
customer cancellation is no longer allowed.
Admin cancellation requires a reason when fulfilment is impossible.
The blueprint confirms this lifecycle and cancellation boundary. 

26. ORDER STATUS INTEGRITY
Statuses must move forward logically.
Do not allow arbitrary reverse transitions such as:
Delivered → Shipping
or:
Preparing → Confirmed
If a serious exceptional correction is required after a completed/reached status, it must not be handled through casual reverse-status editing.
Historical information must remain reliable.

27. MY ORDERS
Customers must be able to see:
current orders 
previous orders 
order status 
order details 
cancellation information where applicable 
relevant payment status 
The customer should be able to understand what is happening with an order without repeatedly contacting the seller.

28. ORDER DETAILS
Historical order information must remain meaningful.
The order must preserve the delivery address used for that order even if the customer's current address changes.
The blueprint explicitly requires historical order delivery information to remain part of the order record. 

29. REVIEWS
A customer can review a product only after a qualifying delivered purchase.
Review flow:
Delivered order
      ↓
Eligible customer
      ↓
Submit review
      ↓
Admin review
      ↓
Approve
      ↓
Public product page
Unapproved reviews must not appear publicly.
Admin should not casually edit customer-written review content.
The approval mechanism exists for moderation, not for selectively showing only positive reviews. The blueprint explicitly specifies approval/rejection before public display. 

30. NOTIFICATIONS
Customer notifications should communicate relevant events.
Examples:
order confirmation/status changes 
cancellation 
product request response 
review-related information 
Admin notifications should identify:
new order 
new product request 
new review 
customer cancellation 
Notifications primarily act as attention indicators directing the user to the relevant area. 

31. PROFILE
Customer profile should provide the information necessary for:
account details 
delivery information 
maintaining the primary/default address 
The current primary address may be edited.
Historical orders must not be changed simply because the profile address changes.

32. ADMIN AUTHENTICATION
There is only one admin for the MVP.
There must not be public admin registration.
Admin credentials/configuration must be securely configured through the backend/environment.
Never hardcode admin credentials in frontend source.
Admin must authenticate before accessing the dashboard.
The blueprint explicitly requires secure backend/environment-based admin credentials.

1. MASTER RULE
This is the most important rule for the entire implementation:
DearThreado must be implemented according to this specification and the supplied visual references. The implementation tool must not independently invent, redesign, remove, replace, or add functionality, business rules, navigation, visual identity, or features.
If something is technically unclear but does not affect the approved product decision, the implementation tool may choose a technically sound solution.
If a decision would change the product itself:
STOP → ASK → DO NOT INVENT.
The blueprint itself defines the project as a working responsive full-stack handmade/personalized gifting application with customization, cart, COD, manual order tracking, admin management, requests, reviews and notifications.

5. CORE DIFFERENTIATION
DearThreado is not simply another gifting website.
The major identity pillars are:
1. Handmade-first
Handmade products are not an occasional category.
Handmade is a core identity.
The platform should primarily communicate:
Handmade + Personal + Meaningful + Special
Existing gifting platforms may contain handmade cards, bouquets and crafts, but DearThreado's identity is specifically centered around handmade gifting.
2. Connection
The emotional relationship between:
person → thought → creation → gift → memory
is central.
3. Personalization
Customization belongs directly inside the product/order journey.
4. Organized discovery
The customer should clearly understand:
Category → Subcategory → Product
rather than being overwhelmed by a huge random product marketplace.
5. Product Request / Feedback
Customers can tell DearThreado what they are imagining when they cannot find it.
This creates a feedback loop for future products.
The original blueprint also identifies personalization, product-specific customization, multi-product cart customization and customer requests as major differentiating elements.

Authentication
Required.

Explain that registration/login is needed to keep the request connected to their account.

Data relationship

Admin

view requests 
manage requests 
respond 
track request status/communication

22. DYNAMIC CUSTOMIZATION
Customization is product-specific.
The admin controls which customization fields apply to each product.
Therefore:
Product A
 ├── Message
 ├── Color
 └── Photo

Product B
 ├── Size
 └── Custom Text
These are examples of the mechanism, not a locked universal field list.
The system must not force identical customization options onto every product.

23. MULTI-PRODUCT CART
A customer can add multiple products.
Each cart item must preserve its own customization.
Example:
Cart

Product A
Customization A

Product B
Customization B

Product C
Customization C
Customization must not accidentally merge between products.
The blueprint specifically identifies multi-product cart support with independent product customization.

Product Request / Feedback

      ↓
Login / Register
      ↓
Successful authentication
      ↓
Return customer to previous intended flow

Your first DearThreado order deserves a little connection. Create an account or log in to continue.

32. ORDER CANCELLATION
Customer cancellation is allowed only:
before Preparing
Once the order reaches:
Preparing
customer cancellation is no longer allowed through the normal flow.

33. ORDER STATUS INTEGRITY
Status must only move forward.
Example:
Placed → Confirmed → Preparing → Shipping
Allowed.
But:
Shipping → Preparing
Not allowed.
If an order has already reached a later/completed stage and an exceptional correction is genuinely required, it must not be handled through an ordinary backward status button.

34. ORDER HISTORY
Customer must see:
Current orders
with their active statuses.
Previous orders
including delivered/completed history.
Historical order information must remain meaningful even if the customer's current profile information changes.
The blueprint explicitly requires order details and preservation of order-related historical information such as delivery address.
